# BLE Log Console User Guide

## Introduction

BLE Log Console is a terminal-based tool for real-time capture and parsing of ESP BLE logs. It supports **UART** and **SPI Bridge** transport modes, displays parsed logs in an interactive TUI, and saves raw binary data for offline analysis.

- **UART mode** receives logs through a serial port. It is suitable for quick debugging, critical logs, and lower log traffic.
- **SPI Bridge mode** receives logs through a BLE Log SPI USB Bridge device. It is suitable for higher log traffic or more stable long-running captures.

## Prerequisites

### 1. UART firmware configuration

Enable `CONFIG_BT_LOG_CRITICAL_ONLY` in the existing project and confirm the following options:

```text
CONFIG_BLE_LOG_PRPH_UART_DMA=y
CONFIG_BLE_LOG_PRPH_UART_DMA_PORT=0
CONFIG_BLE_LOG_PRPH_UART_DMA_BAUD_RATE=3000000
CONFIG_BLE_LOG_PRPH_UART_DMA_TX_IO_NUM=0
```

> Notes:
> - `CONFIG_BLE_LOG_PRPH_UART_DMA_TX_IO_NUM` sets the GPIO for the **UART TX signal**. The default value is `0`.
> - If UART0 is already used by another function, adjust `CONFIG_BLE_LOG_PRPH_UART_DMA_PORT` and the TX GPIO according to the actual hardware.
> - The baud rate selected in BLE Log Console must match `CONFIG_BLE_LOG_PRPH_UART_DMA_BAUD_RATE`.

UART wiring:

```text
ESP32 TX GPIO  ->  USB-Serial RX
ESP32 GND      ->  USB-Serial GND
```

When UART PORT 0 is used, firmware wraps `ESP_LOG` output in BLE Log frames (`REDIR` source). The console decodes those frames as plain text logs.

### 2. SPI Bridge firmware configuration

SPI Bridge mode requires an additional BLE Log SPI USB Bridge device. The Bridge forwards BLE SPI Log data generated by the target device to the PC. It is currently supported by `ESP32P4`.

You can get a Bridge device in either of the following ways:

- Flash an `ESP32P4` development board on the [Bridge firmware download](https://espressif.github.io/esp-launchpad/?flashConfigURL=https://dl.espressif.com/ble/ble_log/spi_bridge_bin/launchpad.toml&crossDomain=true) page.
- Purchase one through official channels, or apply for a trial device through business or technical support.

> Note: The Bridge device is an additional adapter device. It cannot be the same device that generates BLE Log data.

Enable BLE Log and SPI Master DMA output in the target project:

```text
CONFIG_BLE_LOG_ENABLED=y
CONFIG_BLE_LOG_PRPH_SPI_MASTER_DMA=y
```

Configure these GPIOs according to the actual circuit:

```text
CONFIG_BLE_LOG_PRPH_SPI_MASTER_DMA_MOSI_IO_NUM
CONFIG_BLE_LOG_PRPH_SPI_MASTER_DMA_SCLK_IO_NUM
CONFIG_BLE_LOG_PRPH_SPI_MASTER_DMA_CS_IO_NUM
```

Default Bridge wiring:

| Target signal | Bridge pin |
|---------------|------------|
| MOSI | IO 4 |
| SCLK | IO 5 |
| CS | IO 6 |
| GND | GND |

> Notes:
> - The GPIO configuration must match the actual wiring.
> - Both devices must share GND, otherwise data reception may be abnormal.
> - `CONFIG_BLE_LOG_ENABLED` is the global BLE Log switch. If it is not enabled, the PC side will not receive BLE Log data.

## Getting Started

### Quick Start

Prepare the source environment once, then use the launcher script. The launcher forwards all arguments to `console.py`:

```bash
# Linux
./install.sh
./run.sh

# Windows
.\install.bat
.\run.bat
```

Without arguments, the tool opens the **Launch Screen**, where you can:

- Select transport mode: UART or SPI Bridge
- Select an endpoint detected for the current mode
- Select baud rate in UART mode
- Set the log directory
- Press **Connect** to start capture

The Launch Screen adapts to smaller terminal windows and can scroll when needed.

### Command-line launch

List available endpoints:

```bash
python console.py ports
python console.py ports --mode uart
python console.py ports --mode spi
```

UART examples:

```bash
python console.py --mode uart --port /dev/ttyUSB0
python console.py --mode uart --port /dev/ttyUSB0 --baudrate 3000000 --log-dir ./logs
```

Windows UART example:

```bat
python console.py --mode uart --port COM3
```

SPI Bridge example:

```bash
python console.py --mode spi --port <PORT>
```

`spi` is an alias for `spi_usb_bridge`. On Linux, SPI Bridge endpoint names usually look different from UART serial-port names. Use the endpoint printed by `ports --mode spi`.

### CLI Options

| Option | Short | Default | Description |
|--------|-------|---------|-------------|
| `--mode` | `-m` | `uart` | Transport mode: `uart`, `spi`, or `spi_usb_bridge` |
| `--port` | `-p` | optional | Transport endpoint. Omit it to use the Launch Screen |
| `--baudrate` | `-b` | `3000000` | UART baud rate; must match firmware configuration |
| `--log-dir` | `-d` | `./logs` | Directory where capture files are saved |
| `--debug` | none | off | Show extra parser, traffic, and firmware-state debug events |

Subcommands:

| Command | Description |
|---------|-------------|
| `ports` | List UART and SPI Bridge endpoints; accepts `--mode` |
| `ls` | List `ble_log_*.bin` captures in a directory |

`--output/-o` is kept as a hidden compatibility option. Prefer `--log-dir`.

## Saved Files

Captures are saved to the `logs` directory under the current working directory by default:

```text
ble_log_YYYYMMDD_HHMMSS.bin
```

When UART PORT 0 outputs `REDIR` text logs, the console also saves:

```text
ble_log_YYYYMMDD_HHMMSS_console.log
```

The saved paths are printed after the app exits.

## UI Overview

The interface mainly contains a log view and a status panel.

### Log View

The log view scrolls in real time and shows:

- **`[INFO]`**: connection, output path, capture progress, and other user notices
- **`[WARN]`**: firmware-reported frame loss, no data, undecodable data, or realtime parser lag
- Plain text: UART PORT 0 `ESP_LOG` redirect output

Non-debug mode hides most internal state and keeps the log view focused on user-facing notices.

### Status Panel

The status panel is fixed at the bottom and updates in real time:

```text
Status: RECEIVING | Press h for help
RX: 1.2 MB  Frames: 12345  Speed: 2.34 Mbps  Max: 2.80 Mbps  Rate: 3421 fps  Lost: 12 frames, 480 B
```

- **Status**: CONNECTED, RECEIVING, IDLE, or DISCONNECTED
- **RX / Frames**: captured raw bytes and parsed BLE Log frame count
- **Speed / Max**: current and peak transfer speed
- **Rate**: current frame rate
- **Lost**: firmware-reported lost-frame statistics

High realtime traffic notices mean live parsing or UI display may temporarily lag behind raw capture. Raw `.bin` data is saved before parsing; if raw saving itself cannot keep up, the app reports a raw writer or reader backpressure error.

In narrow terminals, the status panel switches to a compact display. During normal operation, `frames` should keep increasing, transfer speed should not be 0, and capture-size prompts should appear after enough data is received.

## Keyboard Shortcuts

| Key | Action |
|-----|--------|
| `q` | Quit |
| `Ctrl+C` | Quit |
| `c` | Clear the log view |
| `s` | Toggle auto-scroll |
| `d` | View received log statistics |
| `m` | View buffer usage |
| `h` | Show shortcut help |
| `r` | Reset the target device; not supported in SPI Bridge mode |

### Frame Statistics Detail (`d` key)

Press `d` to open a modal overlay with two live tables refreshed every second.

**Firmware Counters** show firmware-reported writes and buffer loss:

| Source | Written Frames | Written Bytes | Buffer Loss Frames | Buffer Loss Bytes |
|--------|----------------|---------------|--------------------|-------------------|
| LL_TASK | 12345 | 56.7 KB | 5 | 200 B |
| HOST | 456 | 12.1 KB | - | - |

**Console Measurements** show console-side receive and burst metrics:

| Source | Received Frames | Received Bytes | Average Frames/s | Average Bits/s | Peak Frames/10ms | Peak Bits/s |
|--------|-----------------|----------------|------------------|----------------|------------------|-------------|
| LL_TASK | 12340 | 56.5 KB | 412 | 1.54 Mbps | 8 | 1.92 Mbps |

### Buffer Utilization (`m` key)

Press `m` to show per-LBM (Log Buffer Manager) utilization reported by the firmware:

| Pool | Idx | Name | Peak | Total | Util% |
|------|-----|------|------|-------|-------|
| COMMON_TASK | 0 | spin | 3 | 4 | 75% |
| COMMON_TASK | 1 | atomic[0] | 4 | 4 | 100% |

`Util%` is `Peak / Total`. 100% is highlighted because the buffer pool was fully occupied and may cause frame loss.

## Building Standalone Executable

Use the build scripts to package BLE Log Console as a single-file executable:

```bash
# Linux
./build.sh

# Windows
.\build.bat
```

Run `install.sh` or `install.bat` once before building. The build scripts reuse the prepared local environment, build the executable, place it in the current working directory, and clean up intermediate files.

The build scripts use the current `VERSION` for the output executable name and do not increment the version automatically. Output executable names include platform and version, for example:

```text
ble_log_console_ubuntu_v1.0.3
ble_log_console_windows_v1.0.3.exe
```

To adjust the version while packaging, either update `VERSION` manually first or run `build_exe.py` directly:

```bash
python build_exe.py                 # Use current VERSION, do not bump
python build_exe.py --bump-patch    # Bump patch after a successful build
python build_exe.py --version 1.2.3 # Use an explicit version without modifying VERSION
```

## Troubleshooting

### Device is not shown in the port list

- Check whether the device is powered on.
- Check whether the port is already occupied by another program.
- In UART mode, verify the serial connection.
- In SPI Bridge mode, verify SPI wiring and shared GND.
- On Linux, if using SPI Bridge, make sure the USB permission rule has been installed once by running `sudo ./ble_log_console_ubuntu` or an equivalent setup step, then replug the Bridge device.

### The program starts, but no logs appear

- Check whether the selected transport mode is correct.
- Check whether the selected port is correct.
- Confirm that BLE Log is enabled in the ESP firmware.
- In UART mode, make sure the selected baud rate matches firmware configuration.
- In SPI Bridge mode, make sure the target firmware GPIOs for MOSI, SCLK, and CS match the actual wiring.

### Buffer overflow warning appears

This means the tool has received data, but no valid BLE Log frames were decoded from the internal buffer. Check transport mode, baud rate, firmware configuration, and hardware wiring first.

### Frame loss is severe or High realtime log traffic appears

- Press `d` to inspect per-source loss.
- Press `m` to inspect buffer usage.
- If only High realtime log traffic appears, without a raw writer or backpressure error, raw capture is still continuing and live stats/display may simply lag.
- In UART mode, check baud rate and serial adapter capability.
- In SPI Bridge mode, check the Bridge device, SPI wiring, and firmware GPIO configuration.
- Increase firmware BLE Log buffers or LBM count according to the statistics.

### No ESP_LOG output

- `ESP_LOG` redirect text is only shown for UART PORT 0.
- Confirm the firmware has `CONFIG_BLE_LOG_PRPH_UART_DMA_PORT=0`.
- Logs are flushed by a 1-second periodic timer, so there may be a short delay.
